Trello's data model (lists + cards, no native custom fields on free tier, no MCP precedent within atelier) is the simplest of the three but also the least structured. Planned per the operator's 2026-07-07 "plan everything, no exceptions" instruction; flagged for confirmation at batch-approval.

## Approach

1. **Auth/transport.** Trello REST API (`api.trello.com`) with an API key + token — no MCP precedent, same credential-handling gap noted in `.plan/4.md` for Jira (new pattern needed, or reuse whatever generic external-credential mechanism gets built for Jira, if that lands first — worth sequencing after `.plan/4.md`'s decision rather than solving credential storage twice).
2. **Mapping.** Each roadmap task → one Trello card. Bucket (`roadmap`/`in_progress`/`history`) → moving the card between three lists (`stateMap`-configurable list IDs in `.roadmap.json`, same convention as the other backends). Priority → a label (Trello's built-in colored labels, e.g. `P0`=red, `P1`=yellow, `P2`=green — configurable). `Ready` → a label (Trello Free has no custom fields; Trello Premium/Business does, but assuming the lowest common tier keeps this backend usable without requiring a paid plan).
3. **Plan storage.** Same backend-resident pattern: delimited section in the card description.
4. **`RoadmapBackend` contract.** Full implementation per `docs/RoadmapBackend.md`, mirroring the other two backends' shape.
