# Plan — #3 GitHub Issues backend — map ROADMAP/IN_PROGRESS/HISTORY to repo issues + labels

- **Status:** ready (approved — product lead, batch approval via AskUserQuestion, 2026-07-07)
- **Type / priority / estimate:** feat · P2 · ~6h

> ⚠️ **This item's own ROADMAP.md section says it should "materialize into a task once the multi-backend foundation (TASK_001) is proven and a concrete user need is confirmed."** TASK_001 shipped (v0.2.0, 2026-05-23) and has since been dogfooded successfully via the `linear` and `github-project` backends (both live and in production use per `atelier-dev`'s own tracking) — the "foundation proven" half of the trigger is satisfied. The "concrete user need confirmed" half is **not** independently verified here; no operator/user has been observed asking for a GitHub-Issues-native backend specifically (as opposed to the `github-project` backend atelier-dev already uses, which is a different mapping — issues+labels vs a Projects v2 board). Planned per the operator's 2026-07-07 "plan everything, no exceptions" instruction; flagged for confirmation at batch-approval.

## Approach

Add `GitHubIssuesBackend` implementing the existing `RoadmapBackend` contract (`docs/RoadmapBackend.md`), following the same shape as `GitHubProjectBackend` (M9.2) and `LinearBackend` (M9.1) before it — this backend already has two working precedents to mirror, which substantially de-risks the build:

1. **Mapping.** Each roadmap task → one GitHub Issue. Bucket (`roadmap`/`in_progress`/`history`) → labels `status:roadmap` / `status:in-progress` / `status:done` (as the task bullet itself specifies), swapped via `gh issue edit --add-label/--remove-label` on `moveTask`. Priority (P0/P1/P2) → labels `priority:P0` etc. `Ready` → a dedicated label (`ready`) since Issues have no custom-field equivalent to a Project's `Ready` field.
2. **Plan storage.** Per `TASK_006`/atelier `#37`'s now-established pattern (backend-resident plans), the plan lives in the issue body's delimited `<!-- atelier:plan:start -->`/`<!-- atelier:plan:end -->` section — `setPlan`/`getPlan` implemented the same way `GitHubProjectBackend` does it (issue body vs Project-item body — same technique, different API surface).
3. **`listTasks`/`getTask`.** `gh issue list --label status:roadmap --json number,title,body,labels` / `gh issue view <n> --json ...`, translating labels back into the `RoadmapBackend` task-record shape.
4. **Offline mirror.** Reuse the existing offline-mirror mechanism (`.roadmap.json` → `offlineMirror: true`) already proven for `linear`/`github-project`.
5. **Command wiring.** Extend `/create-roadmap --backend github-issues` and `/migrate-roadmap` per the existing backend-selection pattern (M9.2c did this for `github-project`).

## Acceptance criteria

- [ ] `GitHubIssuesBackend` implements the full `RoadmapBackend` contract (`listTasks`, `getTask`, `moveTask`, `appendHistoryEntry`, `setReady`/`getReady`, `setPlan`/`getPlan`).
- [ ] `/create-roadmap --backend github-issues` scaffolds a working config against a real GitHub repo.
- [ ] End-to-end: create a task issue → plan it (`setPlan`/`Ready`) → claim it (`moveTask` roadmap→in_progress) → close it (`appendHistoryEntry`, in_progress→history) all via the backend, no local files touched.
- [ ] Offline mirror works per the existing pattern.

## Risks / open questions

- **Confirmed-user-need gap (see banner above)** — the primary open question is whether this backend duplicates value already covered by `github-project` (which atelier-dev itself already uses) closely enough that building it isn't worth the ~6h before a real requester exists.
- **Label-based `Ready`/priority is less structured than a Project's custom fields** — GitHub Issues has no native single-select custom field outside Projects, so this backend leans entirely on labels, which are easier to fat-finger (typo a label name) than a Project's constrained field options. Worth a validation step (`gh label list` check) before first use per repo.
