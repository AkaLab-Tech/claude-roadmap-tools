# Plan — #4 Jira backend — map ROADMAP/IN_PROGRESS/HISTORY to Jira issues + workflow states

- **Status:** ready (approved — product lead, batch approval via AskUserQuestion, 2026-07-07; operator explicitly accepted proceeding without a confirmed user — see banner below)
- **Type / priority / estimate:** feat · P2 · ~8h (external API + auth, no MCP precedent unlike Linear/GitHub)

> ⚠️ Same "materialize once a concrete user need is confirmed" trigger as `.plan/3.md` — **no confirmed Jira user is known**, and unlike the GitHub Issues backend, this one has **no existing MCP or precedent backend to mirror** (Linear and GitHub both went through an MCP; Jira would need either a dedicated MCP server or direct REST API + auth handling atelier doesn't have today). This is the least de-risked of the three deferred backends. Planned per the operator's 2026-07-07 "plan everything, no exceptions" instruction; strongly flagged for confirmation at batch-approval — recommend this one specifically stays un-readied until a real requester appears, given the auth/infra cost of building it speculatively.

## Approach

1. **Auth/transport decision (the load-bearing open question).** Two paths: (a) a Jira MCP server, if/when one becomes available with sufficient tool coverage (issue CRUD, transitions, custom fields) — mirrors how `LinearBackend` uses the Linear MCP; (b) direct Jira REST API v3 (`https://<site>.atlassian.net/rest/api/3/...`) with API-token auth stored the way atelier stores other integration credentials (per-project `.env`, never committed — see `CLAUDE.md` secrets handling). Recommend (a) if a maintained Jira MCP exists at build time (consistency with the rest of the backend family); fall back to (b) otherwise, accepting the added auth-handling surface.
2. **Mapping.** Each roadmap task → one Jira issue. Bucket → workflow status transition (`roadmap`→ configurable "To Do"-equivalent, `in_progress`→"In Progress"-equivalent, `history`→"Done"-equivalent) via `stateMap` in `.roadmap.json`, mirroring `GitHubProjectBackend`'s `stateMap` convention exactly. Priority → Jira's native priority field. `Ready` → a custom field or a label, depending on what the target Jira instance's admin permissions allow (a non-admin API token often cannot create custom fields — needs a fallback to a label/component).
3. **Plan storage.** Same backend-resident pattern as the other two backends: delimited section in the issue description.
4. **`RoadmapBackend` contract.** Implement `listTasks`/`getTask`/`moveTask`/`appendHistoryEntry`/`setReady`/`getReady`/`setPlan`/`getPlan` per `docs/RoadmapBackend.md`.

## Risks / open questions

- **No confirmed user (see banner) — recommend NOT readying this without one.** Building speculative auth/credential-handling infrastructure for zero known consumers is a materially different risk than the GitHub Issues backend (which reuses existing `gh` auth atelier already has).
- **Custom-field permission risk** — a non-admin Jira API token frequently cannot create the `Ready` custom field; the design must degrade to a label/component fallback, adding branching complexity.
- **No MCP precedent** raises both build cost and ongoing-maintenance cost relative to the Linear/GitHub-Project backends.
