# Plan — #6 `RoadmapBackend.setPlan` / `getPlan`

- **Status:** ready (approved — product lead)
- **Type / priority / estimate:** feat · P1 · ~TODO (small — prose-only, 4 files, fits the size budget)
- **blocked_by:** none

## Approach

Add two new operations — `setPlan(id, markdown)` and `getPlan(id)` — to the `RoadmapBackend`
contract and its three shipped backends, mirroring the existing `setReady` pattern exactly.
This is a pure-prose change (crt ships no compiled code; the "implementation" is the contract
doc plus the SKILL.md backend-operation prose). The plan content is stored backend-resident so
atelier (#37) no longer needs a committed `.plan/<id>.md` for remote backends.

Storage model, per backend:
- **`GitHubProjectBackend`** — the plan lives in the item body, fenced by a delimited section
  `<!-- atelier:plan:start -->` … `<!-- atelier:plan:end -->`, written/read via the existing
  item-write / item-fetch (`projects_write` / `projects_get`) roles.
- **`LinearBackend`** — the same delimited section, inside the issue description, via issue-fetch /
  issue-update.
- **`FilesBackend`** — the tracked `.plan/<id>.md` file (atelier's existing convention), so the
  contract is uniform across all three backends.

Work order (one coherent change set, reviewable as a single diff):

1. **`docs/RoadmapBackend.md`** — add a `### setPlan(id, markdown)` and `### getPlan(id)` block to
   the Operations section, immediately after `### setReady` (currently lines 140–149), using the
   same Inputs / Returns / Side effects / Atomicity / Errors / per-backend layout. Define the
   delimiter semantics once, in the contract, as the canonical reference:
   - **Missing markers** → "no plan": `getPlan` returns empty/none (not an error); `setPlan`
     appends a fresh `<!-- atelier:plan:start -->…<!-- atelier:plan:end -->` section to the body.
   - **Duplicate markers** → first match wins: `getPlan` reads the first pair; `setPlan` rewrites
     the content of the first pair and leaves trailing duplicates untouched (documented as a
     known-degenerate case, not auto-repaired).
   - `setReady`-style errors: `task-not-found`, `backend-unavailable`. `setPlan` is a single
     body/description/file write — atomic by construction; `getPlan` is read-only.
   Then thread the new field through the cross-cutting sections:
   - **Round-trip of tracked fields** table (lines 245–253): add a `plan` row — remote
     representation = delimited `atelier:plan` section in item body / issue description; files
     representation = the tracked `.plan/<id>.md`.
   - **Reverse reconstruction** (lines 216–273) + **Lossiness note** (266–273): state that the
     `atelier:plan` section is *extracted out of* the body during reconstruction (so it never
     bleeds into `roadmap/TASK_NNN_*.md`) and materialized as `.plan/<id>.md` — i.e. it is
     **lossless**, not dropped. Contrast with the genuinely-lossy remote-only metadata already
     listed (backend ids, assignees, comments).
   - **Versioning** (287–295): record the additive operation per the "non-breaking additions …
     must be documented in the relevant operation section" rule, and note the minor bump.

2. **`skills/roadmap-tracking-flow/SKILL.md`** — add a `### setPlan(id, ...) / getPlan(id)`
   subsection in each of the three Operations sections, mirroring where `setReady` already sits:
   - `Operations (FilesBackend)` after `### setReady` (lines 245–254): read/write `.plan/<id>.md`;
     missing file → "no plan".
   - `Operations (LinearBackend)` after its `### setReady` (lines 378–389): delimited section in
     the issue description via issue-fetch / issue-update; `offlineMirror: true` mirrors the plan
     into the local `.plan/<id>.md`, bundled with the Linear call (parallel to how `setReady`
     mirrors the `[ready]` token).
   - `Operations (GitHubProjectBackend)` after its `### setReady` (lines 508–517): delimited
     section in the item's draft/linked-issue body via item-fetch / item-field-update; same
     offline-mirror behaviour.
   - **Mirror auto-refresh on activation** (533–627): in the refresh procedure, when regenerating
     local files from a remote item's body, the `atelier:plan` section is split out of the body
     before writing `roadmap/TASK_NNN_*.md` and materialized as `.plan/<id>.md`, so the refreshed
     mirror never carries the plan markers inside the task file.

3. **`commands/migrate-roadmap.md`** — make the migration matrix lossless for the plan field:
   - **5d `<remote> → files`** (step 5d.4, line 170, alongside the `backend`/`backendId` strip):
     strip the `atelier:plan` delimited section out of the reconstructed body and write it to
     `.plan/<id>.md`; mention it in the 5d.3 reconstruction plan preview and the 5d.6 / Fidelity
     lossiness notes as **preserved (round-trips)**, not dropped.
   - **5b/5c `files → <remote>`** (push loops, ~lines 88 / 134): when a committed `.plan/<id>.md`
     exists for a task, fold its content into the new item body / issue description as a fresh
     `atelier:plan` delimited section during the push.
   - Update the **Fidelity** "Preserved (round-trips losslessly)" lists (lines 188–221) to add the
     plan section.

4. **`.claude-plugin/plugin.json`** — bump `version` `0.7.0` → `0.8.0` (additive minor: two new
   public contract operations).

## Risks / open questions

- **Which id keys the `.plan/<id>.md` filename for `FilesBackend`.** The contract's canonical
  `FilesBackend` id is `TASK_NNN`, but atelier's existing convention is `.plan/<numeric-id>.md`
  (e.g. `.plan/6.md`). The plan should state explicitly which handle names the file (recommend the
  same `TASK_NNN`/`#id` human handle used elsewhere) so atelier #37 and the migration paths agree.
- **Versioning tension.** The doc's own Versioning section says non-breaking *additions* do **not**
  require a version bump (only documentation). The task asks for an additive **minor** bump anyway.
  Recommend honoring the task (new public operations warrant 0.8.0) and adding a one-line
  versioning note rather than a full migration section — confirm this is the product lead's intent.
- **`setPlan` rewrite vs append semantics.** Confirm the desired behaviour when a body already has
  a plan section: rewrite-in-place of the first marker pair (recommended) vs append. The plan
  specifies rewrite-first-pair; flag for sign-off.
- **HISTORY.md migration note.** The contract's Versioning section also lists a `HISTORY.md`
  migration note for breaking changes. This is additive (non-breaking), so no migration note is
  strictly required, but a `HISTORY.md` entry for the 0.8.0 bump rides on the implementing PR per
  the pre-merge tracking rule — confirm scope.
- **Degenerate duplicate markers.** "First match wins" leaves trailing duplicate sections in the
  body untouched. Confirm the product lead is comfortable documenting this as a known-degenerate
  case rather than specifying auto-cleanup.

## Decisions (product-lead approved — 2026-06-30)

The four open questions are resolved as follows; the implementer follows these:

1. **`.plan/<id>.md` filename handle** → the **numeric `#id`** (`.plan/6.md`, `.plan/34.md`), matching atelier's existing convention and #37's worktree-materialize step. The contract states the numeric id keys the file.
2. **Version bump** → honor the task: `0.7.0 → 0.8.0` (new public operations), with a one-line versioning note (no full migration section — the change is additive/non-breaking).
3. **`setPlan` semantics** → **rewrite-in-place of the first marker pair**; trailing duplicate sections are left untouched.
4. **Duplicate markers** → **first match wins**, documented as a known-degenerate case (no auto-cleanup).

not an opt-out.
